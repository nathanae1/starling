# Plan 15 — Self-hostable headless Linux relay

A **single-binary** Rust service the Owner runs on a Linux box they already
own (Proxmox LXC primary target). Hosts N independent Owners, partitioned
by pubkey. Each paired Owner gets a fresh `.onion` (the relay's own,
generated server-side at pair time) which becomes an additional endpoint
on the Owner's Connection Card. Followers prefer a phone↔phone path and
reach the relay's onion only when the phone is asleep/offline.

> **Design history.** A prior revision of this plan used OnionBalance v3
> to give each Owner one shared `.onion` between phone and relay. That
> approach doesn't survive contact with OB v3's actual key model — see
> [15b-r3-multi-endpoint-decision.md](15b-r3-multi-endpoint-decision.md)
> for the architectural decision that produced the current shape. The
> related Arti-HS-key-export spike is in
> [15a-arti-hs-key-export-spike.md](15a-arti-hs-key-export-spike.md) —
> no longer a Plan 15 blocker under the current design but kept as
> reference.

## Dependencies

Plan 07 (HTTP server), Plan 11 (Tor / Arti), Plan 13 (the
`pending_card_distributions` Card-fanout pattern, reused here to push
the updated Card to Followers after pairing), Plan 14 (lifecycle —
phone-side backfill triggers).

## Context

Starling's architecture promises a "self-hosting gradient": phone-to-phone
→ old phone as relay → standalone relay. The phone-as-relay tier was
abandoned (OEM kills, Doze, no iOS analog). The standalone tier is shaped
for a Linux box the Owner already runs (Proxmox LXC primary target).

Two cumulative architectural shifts beyond just picking a language:

1. **Multi-owner.** One relay process hosts N independent Owners, each
   paired separately. Data partitioned by pubkey. No aggregation, no
   cross-Owner reads.
2. **Multi-endpoint Connection Cards.** The relay's per-Owner `.onion` is
   added to the Owner's Card as an extra endpoint
   (`Endpoint(type:'relay', address: ...)`). Followers rank it below
   every phone↔phone tier and use it only when the phone is
   unreachable. No shared keys, no OnionBalance, no
   descriptor coordination. If the relay is offline Followers fall back
   to the phone's `.onion` automatically — and vice versa.

The wire protocol stays language-agnostic: Ed25519 detached over
`blake2b_256(body)` in `X-Starling-Sig` / `X-Starling-Pubkey` headers,
CBOR bodies.

## Decisions (resolved with user)

| Decision | Choice |
|---|---|
| Language | **Rust** standalone binary |
| Pairing UX | **Web admin UI + CLI token**, both. QR via web, token to stdout for SSH |
| Multi-owner | **Yes**, one relay process hosts N Owners |
| Per-Owner topology | **Each paired relay has its own `.onion`** (generated by the relay at pair time, with its own HS keypair). Followers prefer a phone↔phone path and fall back to the relay's onion only when the phone is unreachable. |
| Tor implementation on the relay | **Embedded Arti** (same `starling-arti` crate the phone uses via FFI). No C-tor, no OnionBalance, single process. |
| Endpoint scope | **Data only**: status, manifest, events, media, pair. Follows/config stays on phones |
| Distribution | musl binary + systemd unit + Proxmox LXC helper + multi-arch Docker image |
| Admin UI auth | localhost-bound default; optional argon2 password for LAN exposure |
| Storage encryption | **Drop SQLCipher** — payloads are client-encrypted; ops handles disk |
| TLS clearnet ingress | **Deferred to v2** — v1 is Tor-only |

## Architecture overview

```
                      Owner A's Connection Card
                      ┌─────────────────────────────────────┐
                      │ pubkey: A_pk                        │
                      │ endpoints:                          │
                      │   { type:'onion', addr: phoneA }    │
                      │   { type:'relay', addr: relayA }    │
                      └─────────────────────────────────────┘
                                  │ Followers prefer phone,
                                  │ fall back to relay
                  ┌───────────────┴──────────────┐
                  ▼                              ▼
        ┌──────────────────┐          ┌──────────────────────────────┐
        │ Owner A's phone  │          │   Owner A's paired relay     │
        │  Arti HS for A   │          │ (one of N Owners on this box)│
        │  serves /status  │          │  Embedded Arti, one          │
        │  /manifest       │          │  RunningOnionService per     │
        │  /events /media  │          │  paired Owner, nickname =    │
        │                  │          │  hex(owner_pubkey).          │
        │  Phone signs +   │          │  Per-Owner axum router on    │
        │  pushes events / │          │  127.0.0.1:<unique_port>     │
        │  media to relayA │          │  serves /status /manifest    │
        │  via /events,    │          │  /events /media + owner-sig  │
        │  /media          │          │  middleware. Single shared   │
        │                  │          │  SQLite (pubkey-partitioned).│
        │                  │          │  Admin onion + web UI for    │
        │                  │          │  pairing / monitoring.       │
        └──────────────────┘          └──────────────────────────────┘
```

Each paired Owner: one onion at the relay, one HS keypair generated by
the relay's Arti (the phone never sees this key), one axum router
bound to a unique loopback port that Arti's reverse-proxy forwards
traffic to.

│   │                                     /health

**Process structure at runtime:** one process. The Rust binary owns
SQLite (single `r2d2::Pool<SqliteConnectionManager>`), runs Arti
embedded for both the admin onion and every paired Owner's onion,
mounts the admin web UI on `bind_admin`, and mounts a per-Owner axum
instance on a unique loopback port for each paired Owner.

Reconfiguration on pair/unpair: launch (or drop) a `RunningOnionService`
on the already-running `TorClient`, start (or stop) the corresponding
axum task. No external process to signal, no config files to rewrite.

## Multi-owner schema

`crates/starling-relay-storage/migrations/0001_init.sql`:

```sql
CREATE TABLE paired_owners (
    pubkey                BLOB PRIMARY KEY NOT NULL,   -- 32-byte Ed25519 pubkey
    label                 TEXT,                         -- admin display name
    paired_at             INTEGER NOT NULL,
    relay_onion_address   TEXT NOT NULL,                -- this paired relay's onion for this Owner
    local_port            INTEGER NOT NULL,             -- loopback port Arti forwards to
    storage_cap_bytes     INTEGER                       -- NULL → global default
);

CREATE TABLE pending_pairings (
    token        BLOB PRIMARY KEY NOT NULL,             -- 32 random bytes
    created_at   INTEGER NOT NULL,
    expires_at   INTEGER NOT NULL,                       -- created + 600s
    consumed_at  INTEGER,
    created_by   TEXT NOT NULL,                          -- 'web' | 'cli'
    label        TEXT
);
CREATE INDEX idx_pending_pairings_expires ON pending_pairings(expires_at);

CREATE TABLE served_events (
    pubkey      BLOB NOT NULL,
    id          TEXT NOT NULL,                          -- plaintext event id
    created_at  INTEGER NOT NULL,
    msg_seq     INTEGER NOT NULL,
    nonce       BLOB NOT NULL,
    payload     BLOB NOT NULL,                          -- raw EncryptedEvent
    PRIMARY KEY (pubkey, id),
    FOREIGN KEY (pubkey) REFERENCES paired_owners(pubkey) ON DELETE CASCADE
);
CREATE INDEX idx_served_events_owner_time ON served_events(pubkey, created_at DESC);

CREATE TABLE served_media (
    pubkey     BLOB NOT NULL,
    hash       TEXT NOT NULL,                           -- hex BLAKE2b-256
    size       INTEGER NOT NULL,
    created_at INTEGER NOT NULL,
    path       TEXT NOT NULL,                           -- relative to data_dir/media/
    PRIMARY KEY (pubkey, hash),
    FOREIGN KEY (pubkey) REFERENCES paired_owners(pubkey) ON DELETE CASCADE
);

CREATE TABLE admin_credentials (
    id            INTEGER PRIMARY KEY CHECK (id = 1),
    password_hash TEXT NOT NULL,                         -- argon2id
    updated_at    INTEGER NOT NULL
);
```

**No `served_follow_requests` table** — follow-request / follow-accept
stay on phones per "follows/config on phones." If both phones are
offline simultaneously, follow-request retries later. The relay's job
is content availability, not follow brokering.

Unpair = `DELETE FROM paired_owners WHERE pubkey = ?`; CASCADE wipes
events + media. The Arti `RunningOnionService` for that nickname is
dropped (Arti unpublishes on drop). HS keystore entry for that
nickname is removed via `KeyMgr::remove`.

SQLite pragmas (applied per connection in the `r2d2` setup hook):
`PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL; PRAGMA busy_timeout=5000`.

## Endpoints (per-Owner axum instance)

Each Owner's `.onion` (the one in `paired_owners.relay_onion_address`)
forwards to one loopback port. Exactly one axum instance per Owner serves
that port. The Owner's pubkey is implicit (constant for that instance)
so no `?pubkey=` query is needed anywhere.

| Path | Method | Auth | Body | Storage | Response |
|---|---|---|---|---|---|
| `/status` | GET | none | — | counts/sizes for this Owner | JSON `{pubkey, version, event_count, media_storage_used}` |
| `/manifest?since=&until=` | GET | none | — | `EventsDao::manifest_page` | CBOR `{events:[{id,created_at}], has_older}` |
| `/events?since=` | GET | none | — | `EventsDao::payloads_since` | CBOR `Envelope` |
| `/media/<hash>` | GET | none | — | `MediaDao::lookup` + file stream | `application/octet-stream` |
| `/events` | POST | owner-sig | CBOR `{items:[{id,payload}]}` | `EventsDao::insert_many` | 202 |
| `/media/<hash>` | POST | owner-sig | raw encrypted bytes | write file + `MediaDao::insert` | 202 |

The `/pair` endpoint lives on a separate **admin onion**, not on any
per-Owner instance. See §"Pairing flow."

**Not implemented** (deferred per "follows/config on phones"):
- `POST /follow-request` — Followers reach the Owner's phone directly.
- `POST /follow-accept`.

**Sig middleware**
(`crates/starling-relay-http/src/middleware/owner_sig.rs`) — verifies
`X-Starling-Sig` over `blake2b_256(body)` with `X-Starling-Pubkey`
matching this instance's owner. 401 on bad sig, 403 on pubkey mismatch
(caller is talking to the wrong instance's onion).

**Zero-knowledge enforcement**: `starling-relay-http`'s `Cargo.toml` has
no `feed-key` / `content-key` / decrypt deps. `tests/zero_knowledge.rs`
walks `cargo-metadata` and fails the build if any transitive dep name
matches those names. Belt + braces.

## Pairing flow

The relay runs a separate admin onion (nickname
`starling-relay-admin`, generated at first run, persisted in Arti's
keystore). It exposes the admin web UI + `/pair` POST endpoint.

```
Admin opens web UI / runs `starling-relay pair --label "phone-1"`
    │
    ▼
Relay inserts pending_pairings(token=rand(32), expires=now+600,
                               label, created_by='web'|'cli')
    │
    ▼
Web UI renders QR encoding starling-relay://pair?card=base64url(CBOR{
    admin_onion_address,
    pairing_token,
    relay_version
})
CLI prints the same token + URL to stdout
    │
    ▼  (Owner's phone scans QR OR types into Settings → Pair a relay)
    │
Phone:
  1. claim = blake2b_256(
        "starling-relay-pair-v1" ||
        owner_pubkey || admin_onion_address || pairing_token
     )
  2. sig = Ed25519.sign(owner_sk, claim)
  3. POST /pair over Tor to admin_onion_address with CBOR:
        { owner_pubkey, pairing_token, sig }
    │
    ▼
Relay /pair handler:
  • Look up pending_pairings by token; 409 if consumed_at, 410 if expired
  • Recompute claim; verify sig with ed25519-dalek; 401 on fail
  • Allocate a free loopback port (lowest unused in 17000-17999)
  • Generate a fresh HS keypair via Arti for this Owner; nickname =
    hex(owner_pubkey). The keypair lives only on the relay.
  • Call client.launch_onion_service(svc_cfg); poll status until
    reachable (~30s typical, 60s timeout → 504 on timeout)
  • INSERT paired_owners(pubkey, label, paired_at,
                          relay_onion_address, local_port, storage_cap_bytes)
  • UPDATE pending_pairings SET consumed_at = now
  • Start the per-Owner axum task bound to local_port
  • Return 200 CBOR { relay_onion_address, relay_id }
    │
    ▼
Phone:
  • Persist paired_relay(relay_id, paired_at, relay_onion_address)
  • Re-sign Connection Card with the new endpoint:
        existing endpoints + Endpoint(type:'relay',
                                       address: relay_onion_address)
  • For each existing Follower: INSERT pending_card_distributions row
    (target_pubkey, cardCbor, sig, createdAt). The next time the
    Follower hits the phone's /manifest, the new Card piggybacks
    (Plan 13 pattern, already implemented).
  • Trigger initial backfill: walk own events + media chronologically,
    push via /events, /media to relay_onion_address. Idempotent
    (PK is (pubkey, id) / (pubkey, hash)).
  • Mark backfill done
```

Token TTL 600s. Single-use. Token capture from the wire is useless
without the Owner's signing key — the sig binds `owner_pubkey` to
`(admin_onion, token)`.

The admin onion is meta-infrastructure; it accepts only `/pair` POSTs
over Tor and serves the admin UI on `bind_admin` (localhost-bound by
default). It must NOT be advertised in any Owner's Card. Enforced by
it living on a separate axum router from any Owner's data router.

## Admin web UI

`crates/starling-relay-admin/`. Five pages, askama templates, embedded
assets via `rust-embed`:

- `/` — paired owners table (pubkey suffix, label, paired_at, event count,
  storage used / cap, onion address, Unpair button). "Add Owner" button.
- `/pair` — server-rendered QR + plaintext token + 5s meta-refresh, plus
  ~30 lines of vanilla JS polling `/api/owners` to redirect on success.
- `/login` — only if `admin_credentials` row exists. `tower-cookies`
  signed session, 24h.
- `/health` — JSON `{status, uptime_seconds, arti_status, owner_count}`
  for monitoring.
- `/api/owners` — JSON list for polling.

Default bind: `127.0.0.1:8088`. README documents `ssh -L
8088:127.0.0.1:8088` as the canonical access pattern. Setting
`admin_password_hash` (via `starling-relay set-password`) enables
LAN-bound use at `bind_admin = "0.0.0.0:8088"`.

`starling-relay pair --label X` talks to the running relay via Unix
socket `${data_dir}/admin.sock` (mode `0600`, parent dir `0700`).
Protocol: line-delimited JSON, single endpoint `POST /pair-token`
with optional `{label}` body, returns
`{token, admin_onion_address, expires_at}`.

## Verification

**Manual end-to-end** (dev laptop + two Android devices + a Linux VM):
1. `docker run -p 8088:8088 -v starling-data:/data ghcr.io/<org>/starling-relay:latest`
   — single process boots, admin onion appears in logs after Arti
   bootstrap.
2. Open `http://localhost:8088` → "Add Owner" → "Phone 1" → QR rendered.
   (Or `docker exec ... starling-relay pair --label phone-1`.)
3. Phone 1: Settings → "Pair a relay" → scan QR. Phone POSTs `/pair`
   over Tor with the simplified claim. Relay verifies, generates a
   fresh HS keypair, launches the new onion service, returns 200 with
   the new `.onion`.
4. Wait ~30s for Arti to publish the new HS descriptor.
5. Phone 1's Connection Card now has two endpoints; Followers receive
   the updated Card next time they hit Phone 1's `/manifest`.
6. From Phone 2 (already following Phone 1), open the feed. Phone 2's
   reachability monitor probes both endpoints; whichever returns first
   wins. With both up, either path works.
7. Publish a post on Phone 1. Phone fans out to Followers + pushes to
   relay (`POST /events` succeeds — admin UI event count increments).
8. **Force-quit Phone 1.** Wait 30s. Phone 2 pulls — phone-onion is
   stale, relay-onion answers. `/manifest` + `/events` served by the
   relay. Post renders.
9. Repeat 2-3 with Phone 3 as a *second* Owner on the same relay.
   Phone 3 gets a different `.onion`. Phone 1's data still fetches
   cleanly; Phone 3's pubkey appears as a second admin-UI row.
10. Admin UI "Unpair" Phone 3 → `sqlite3 starling.db "SELECT count(*)
    FROM served_events WHERE pubkey = X'...'"` returns 0 (CASCADE
    worked); Phone 3's `RunningOnionService` is dropped; the
    corresponding KeyMgr entry is removed.
11. SSH `starling-relay pair --label phone-4` → confirm token printed,
    scannable.

## Risks / open questions

- **Multi-endpoint selection on the Follower side.** ~~Race all onion
  endpoints, or add per-endpoint state?~~ **Resolved (implemented).** The
  phone onion and the relay onion are distinct transport tiers in
  `PeerReachabilityMonitor._priority` (LAN → libp2p-direct → `tor` (phone
  onion) → `relay`), not a single raced bucket. The relay ranks last, so
  a reachable phone↔phone path always wins; selection runs only over
  already-probed-reachable transports, so this never stalls on an asleep
  phone. See `app/starling/lib/sync/peer_reachability_monitor.dart:117`.
- **First-pair publication latency.** ~30s for Arti to publish the new
  onion's descriptor. The `/pair` handler waits synchronously until
  `RunningOnionService::status()` reports the service is reachable,
  with a 60s timeout (→ 504). Acceptable for a one-shot setup
  operation.
- **HS key compromise blast radius.** Each paired relay's HS keys
  live only on that relay. Compromise affects only the relay's
  endpoint, not the phone's. Documented in the spec amendment.
- **Per-Owner Arti onion services cost.** N Owners = N
  `RunningOnionService` instances on one `TorClient` = ~3N intro
  circuits + descriptor maintenance. Fine for 5-20 Owners on a home
  box; out of scope for 100+.
- **Storage cap pruning.** v1: manual via admin UI ("Reclaim space"
  on the Owner row, deletes oldest first up to N% of cap). Auto-prune
  is v2. The phone re-pushes any event the relay 404s on, so manual
  pruning is safe.

## Out of scope

- **TLS clearnet ingress** — v2.
- **`POST /follow-accept` cross-relay write** — v2; trust model for
  accepting writes from a non-paired pubkey needs more design.
- **Standalone Rust relay binary repackaged elsewhere** — this IS that
  binary.
- **Multi-relay redundancy per Owner** — one paired relay per Owner
  for v1 (the wire shape supports more — the Card endpoint list is
  unbounded — but the phone-side pairing UI and fanout iteration are
  single-relay for v1).
- **Relay-to-Relay gossip** — explicitly not a feature.
- **Per-Follower request attribution on the relay dashboard** —
  incompatible with the relay's role; aggregate counts only.
- **Auto-pruning on storage cap exceeded** — v2; v1 is manual via
  admin UI.
